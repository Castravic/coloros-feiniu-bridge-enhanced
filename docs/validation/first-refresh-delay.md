# 本地相册冷启动刷新修复

## 已确认的复现

用户明确：相册已在前台时截图正常；相册关闭期间新增截图或保存图片后，首次打开时图片可能不显示，切后台再返回才刷新。此前体感约 50 秒不能视为固定超时。

2026-10-28，用户确认冷启动试修复包已解决本次问题，并授权 review 和发布。两版真实 APK 契约均经过静态检查；用户确认不能扩大为所有相册版本、所有备份功能的真机验收。

## 定位依据

真实相册 16.50.8 的 `k11$b.invokeSuspend` 和 17.10.7 的 `ActivityLifecycle$addListener$1.invokeSuspend` 只把监听器加入生命周期列表，不回放已经发生的前台事件。本地媒体同步监听器 `loo$b.g` / `fgq$b.g` 则在前台启动时处理待通知 URI，并进入厂商同步队列。

如果本地同步监听器在首次前台事件后才注册，就可能漏掉冷启动补扫。修复在注册协程成功完成后，向主线程投递一次检查：相册已在前台、监听器尚未收到原生启动回调、且从未补调时，调用它原来的 `g()`。正常原生回调先到时跳过，后台注册时不补调，其他生命周期监听器不受影响。

原始入口继续执行厂商的权限、同步条件、去抖和队列逻辑。补调完成日志表示原入口执行完毕，不能单凭该行断言数据库同步已经完成。

## 正式发布边界

- 0.4.3 的 Debug 和 Release 都启用修复。
- 仅精确匹配相册 16.50.8 / 17.10.7，并校验静态前台方法、原生回调和注册协程签名；未知版本跳过。
- 用弱引用记录监听器状态，补调在主线程执行，每个监听器至多一次。
- 单测覆盖正常启动、晚注册、重复注册、并发补调和监听器隔离；真实 APK 测试检查两版方法与字段契约。

## 诊断与对照的限制

关闭 LuckyTool 后的新相册进程没有它的加载记录，先前额外的配置 Hook 等待栈也消失，仍需按本地冷启动问题排查。仅凭作用域表残留记录不能认定模块仍在加载。

早期线程采样被空闲线程池挤占，后续已修正。第二版按类 Hook 共用的 `ekb$a`，可能把相册数据库通知也标为媒体通知，因此不能据此认定某张截图的 MediaStore 通知已送达。第三版按具体注册实例、URI authority 类别和内部分发接收者区分；不记录 URI 路径、文件名、图片内容或 token。

批量诊断默认关闭。仅构建 Debug 时显式指定 `-PrefreshDiagnostics=true` 才启用启动后 90 秒的限时采样；正式 Release 始终关闭。

常规恢复日志：

```text
local startup sync recovery installed version=...
local startup sync registration foreground=true replay=true
local startup sync replay completed source=native-onStarted
```

`replay=false` 说明该监听器本次无需补调。

## 真机回归步骤

1. 安装模块，确认相册作用域启用，强停相册。
2. 在相册外截图或保存图片。
3. 首次打开相册，观察新增图片能否直接出现；不要先切后台。
4. 相册在前台时再截图，确认原有即时刷新正常。
5. 如有问题，再切后台返回，并保留此次模块日志及操作时间。
